This section covers the definition of the network topology in Mininet and the resulting division into two isolated \textit{slices}. The aim is to construct a topology in which hosts can communicate via predefined routes:
\begin{itemize}
    \item The host h1 can communicate only with h3 via the \textbf{upper path};
    \item The host h2 can communicate only with h4 via the \textbf{lower path}.
\end{itemize}

\noindent
For this purpose, the following Mininet configuration has been defined by implementing the constructor of the \lstinline|Mininet.Environment| class, whose logical view is represented in figure \ref{img:network_view}.

\noindent
Given the defined network topology, a \textbf{deterministic} routing approach was implemented within the controller. This design ensures granular control over traffic flows, allowing for the enforcement of static routes that guarantee slice isolation and adherence to predefined network policies.

\textbf{RyuController} is an SDN application based on the OpenFlow 1.3 protocol, designed to manage a network environment emulated via Mininet and Open vSwitch. The application was developed by extending the \lstinline|ryu.base.app_manager.RyuApp| base class. To ensure deterministic forwarding and strict slice isolation, a static addressing scheme was adopted: host MAC addresses are defined as constant strings directly within the class constructor."

\begin{pythoncode}
# Base class extension
class RyuController(app_manager.RyuApp):
    # OpenFlow 1.3 
    OFP_VERSIONS = [ofproto_v1_3.OFP_VERSION]

    def __init__(self, *args, **kwargs):
        super(RyuController, self).__init__(*args, **kwargs)
        
        # Static MAC addresses definition for deterministic routing
        self.h1 = '00:00:00:00:00:01'
        self.h2 = '00:00:00:00:00:02'
        self.h3 = '00:00:00:00:00:03'
        self.h4 = '00:00:00:00:00:04'

    # Utility function to add flow rules to the switches
    def add_flow(self, datapath, priority, match, actions, idle_timeout=0, flag=0):
        ofproto = datapath.ofproto
        parser = datapath.ofproto_parser

        inst = [parser.OFPInstructionActions(ofproto.OFPIT_APPLY_ACTIONS, actions)]
        mod = parser.OFPFlowMod(
            datapath=datapath, priority=priority,
            match=match, instructions=inst,
            idle_timeout = idle_timeout, flags=flag
        )

        datapath.send_msg(mod) # Send the flow modification message to the switch
\end{pythoncode}


The routing strategy implemented in this SDN controller follows a \textbf{proactive} approach. Rather than reacting to packets arriving at the controller, flow rules are pre-installed on all switches during the controller initialization phase, specifically when the \lstinline|switch_features_handler| is triggered upon OpenFlow handshake completion.

This proactive method offers several advantages:
\begin{itemize}
    \item \textbf{Deterministic behavior}: All routing decisions are made statically before any traffic flows through the network, ensuring predictable and consistent packet forwarding;
    \item \textbf{Reduced latency}: Packets are forwarded according to pre-installed rules without requiring controller interaction, eliminating the overhead of reactive packet-in messages;
    \item \textbf{Improved performance}: The controller is not burdened with runtime packet processing, allowing it to manage multiple switches more efficiently;
    \item \textbf{Enhanced slice isolation}: Static rules guarantee that traffic is strictly confined within designated slices, preventing any cross-slice communication regardless of runtime conditions.
\end{itemize}

\noindent
Unlike reactive approaches where the controller would process unknown flows dynamically, this proactive strategy ensures that every switch has complete knowledge of how to forward packets for all host pairs, thus achieving the isolation guarantees required by the network slicing architecture.
When Mininet initiates a switch, it attempts to establish a TCP connection with the Ryu controller. If the connection is successful (i.e. the three-way handshake is completed), the OpenFlow handshake is then initiated. Subsequently, the switch sends a \lstinline|FEATURES_REPLY| message, and the controller executes the \lstinline|switch_features_handler| function.
This function is responsible for installing the flow rules in the switch, which are defined based on the switch's unique identifier (dpid). The flow rules are designed to enforce the predefined routing paths and ensure that traffic is confined within the designated slices of the network.


\begin{pythoncode}
@set_ev_cls(ofp_event.EventOFPSwitchFeatures, CONFIG_DISPATCHER)
def switch_features_handler(self, ev):
    datapath = ev.msg.datapath
    ofproto = datapath.ofproto
    parser = datapath.ofproto_parser
    dpid = datapath.id

    if dpid == 1: # Switch S1
        # UP flow configuration
        port_out_Up = 3 # S1 out port (UP)
        port_in_Up = 1 # S1 in port (UP)

        # Flow IN
        self.add_mac_flow(datapath, self.h1, self.h3, port_out_Up) # Eth H1 to H3 via s1:1 
        self.add_arp_flow(datapath, self.h1, port_out_Up) # ARP  H1 to H3 via s1:1

        # Flow Back
        self.add_mac_flow(datapath, self.h3, self.h1, port_in_Up) # Eth H3 to H1 via s1:3
        self.add_arp_flow(datapath, self.h3, port_in_Up) # ARP from H3  to H1 via s1:3
        
        ##################################################################################
        
        # Down flow configuration 
        port_out_Dw = 4 # S1 out port (DW)
        port_in_Dw = 2 # S1 in port (DW)
        
        # Flow IN
        self.add_mac_flow(datapath, self.h2, self.h4, port_out_Dw) # Eth H2 to H4 via s1:2
        self.add_arp_flow(datapath, self.h2, port_out_Dw) # ARP H2 to H4 via s1:2

        # Flow Back
        self.add_mac_flow(datapath, self.h4, self.h2, port_in_Dw) # Eth H4 to H2 via s1:4
        self.add_arp_flow(datapath, self.h4, port_in_Dw) # ARP H4 to H2 via s1:4

    elif dpid == 2: # Switch S2
        # UP flow configuration
        port_out_Up = 1 # S2 out port (UP)
        port_in_Up = 3 # S2 in port (UP)

        # Flow IN
        self.add_mac_flow(datapath, self.h3, self.h1, port_out_Up) # Eth H3 to H1 via s2:1
        self.add_arp_flow(datapath, self.h3, port_out_Up) # ARP H3 to H1 via s2:1

        # Flow Back
        self.add_mac_flow(datapath, self.h1, self.h3, port_in_Up) # Eth H1 to H3 via s2:3
        self.add_arp_flow(datapath, self.h1, port_in_Up) # ARP H1 to H3 via s2:3

        ##################################################################################

        # Down flow configuration
        port_out_Dw = 2 # S2 out port (DW)
        port_in_Dw = 4 # S2 in port (DW)
        
        # Flow IN
        self.add_mac_flow(datapath, self.h4, self.h2, port_out_Dw) # Eth H4 to H2 via s2:2
        self.add_arp_flow(datapath, self.h4, port_out_Dw) # ARP H4 to H2 via s2:2

        # Flow Back
        self.add_mac_flow(datapath, self.h2, self.h4, port_in_Dw) # Eth H2 to H4 via s2:4
        self.add_arp_flow(datapath, self.h2, port_in_Dw) # ARP H2 to H4 via s2:4

    elif dpid == 3: # Switch 3 (UP)
        port_1 = 1 # S3 in port (UP)
        port_2 = 2 # S3 out port (UP)

        self.add_mac_flow(datapath, self.h1, self.h3, port_2) # Eth H1 to H3 via s3:2
        self.add_arp_flow(datapath, self.h1, port_2) # ARP H1 to H3 via s3:2

        self.add_mac_flow(datapath, self.h3, self.h1, port_1) # Eth H3 to H1 via s3:1
        self.add_arp_flow(datapath, self.h3, port_1) # ARP H3 to H1 via s3:1

    
    elif dpid == 4: # Switch 4 (DW)
        port_1 = 1 # S4 in port (DW)
        port_2 = 2 # S4 out port (DW)

        self.add_mac_flow(datapath, self.h2, self.h4, port_2) # Eth H2 to H4 via s4:2
        self.add_arp_flow(datapath, self.h2, port_2) # ARP H2 to H4 via s4:2

        self.add_mac_flow(datapath, self.h4, self.h2, port_1) # Eth H4 to H2 via s4:1
        self.add_arp_flow(datapath, self.h4, port_1) # ARP H4 to H2 via s4:1    
        
\end{pythoncode}

\noindent
After determining the switch identity with \textit{dpid}, the controller creates the rule through add\_mac\_flow, which is the association (mac\_src, mac\_dst) $\to$ port. Through the add\_arp\_flow rule, we enforce that ARP messages can exit on multiple ports, and it is a rule with higher priority than the one that enforces MAC-based flow. We observe that the ARP packet, which is sent in broadcast, is nevertheless confined within the network \textit{slice}.

\vspace{.3cm}
\begin{pythoncode}
    def add_mac_flow(self, datapath, src, dst, out_port, priority=10): # Utility function to add flow rules based on MAC addresses, specifying the source and destination MAC addresses, the output port, and an optional priority level for the flow rule
        parser = datapath.ofproto_parser

        match = parser.OFPMatch(eth_src=src, eth_dst=dst)
        actions = [parser.OFPActionOutput(out_port)]
        self.add_flow(datapath, priority, match, actions)
    
    def add_arp_flow(self, datapath, eth_src, out_port): # Utility function to add flow rules for ARP packets, matching only the source MAC address and allowing the packet to be output on multiple ports (if out_port is a list), with a higher priority than the MAC-based flow rules to ensure that ARP packets are handled correctly
        parser = datapath.ofproto_parser
        
        match = parser.OFPMatch(eth_src=eth_src, eth_dst="ff:ff:ff:ff:ff:ff", eth_type=0x0806)
        actions = []
        if not isinstance(out_port, list):
            out_port = [out_port]

        for port in out_port:
            actions.append(parser.OFPActionOutput(port))
        self.add_flow(datapath, priority=20, match=match, actions=actions)

\end{pythoncode}
